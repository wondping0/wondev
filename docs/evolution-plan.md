# Update, migration, and evolution plan

wondev writes files into other people's repositories and ships template content those
people then edit. Both keep changing. This document names every thing that can version
independently and the mechanism each one needs.

Conflating them is the standard mistake: a single "version" number cannot describe a tool
whose output lives in someone else's git history.

## What can change independently

| # | Thing | Lives in | Breaks what, when it changes |
| - | ----- | -------- | ---------------------------- |
| 1 | The package | npm | nothing directly |
| 2 | Source format | `.wondev/` layout + frontmatter | user's authored content stops parsing |
| 3 | Manifest format | `.wondev/.manifest.json` | wondev loses track of what it owns |
| 4 | Render output | generated bytes | **every downstream CI turns red at once** |
| 5 | Starter pack | `templates/` | user's edited copies go stale |
| 6 | Target registry | agent paths | output lands in the wrong place |

Row 4 is the dangerous one and the least obvious.

---

## Plan A — Release mechanism

**Problem:** no defined contract for what a version bump means.

SemVer, with the contract written down:

- **MAJOR** — source format breaks, or an output path moves.
- **MINOR** — new targets, new starter skills, **any change to generated bytes**.
- **PATCH** — fixes that leave generated output byte-identical.

The load-bearing rule is that third clause. A "harmless" wording tweak in a renderer makes
`wondev check` fail in every project using wondev. That is never a patch.

Deliverables:

- `CHANGELOG.md` (Keep a Changelog).
- `docs/versioning.md` stating the contract above.
- `.github/workflows/release.yml`: on tag push, run verify, then
  `npm publish --provenance` for a signed supply-chain attestation.
- Release is `npm version minor && git push --follow-tags`; CI does the rest.

Cost: small. Do it before the first publish.

## Plan B — Format version stamps and a migration engine

**Problem:** nothing records which format wrote a project, so nothing can ever migrate it.

Stamp both files:

```yaml
# .wondev/wondev.yaml
schema: 1              # source format version
wondevVersion: 0.1.0   # what last wrote this
```

```json
{ "version": 1, "wondevVersion": "0.1.0", "files": { } }
```

Then an ordered migration list in `src/core/migrate/`:

```ts
interface Migration {
  from: number;
  to: number;
  describe: string;
  apply(root: string): Promise<string[]>;  // paths changed
}
```

- `wondev migrate` runs every pending migration in order. `--dry-run` prints the plan.
- `build` and `check` refuse when `schema < current` and say *"run `wondev migrate`"*.
- **Never auto-migrate.** Migration edits the user's authored source; that requires consent.

**The important part: stamp the versions now, write migrations later.** The stamp is about
thirty lines and is impossible to add retroactively — a project initialised without one is
permanently unidentifiable. The engine can wait until there is something to migrate.

## Plan C — Output-version awareness

**Problem:** when a renderer changes, every user's `wondev check` fails in CI with
"generated file does not match", which reads like *their* mistake.

The manifest already stores a hash per file. Add the wondev version that produced it, and
branch the message:

- installed version == manifest version, content differs → genuine drift, current wording is
  right.
- installed version != manifest version → *"these files were generated by wondev 0.1.0, you
  have 0.2.0 — run `wondev build`"*.

Same failure, but now it is a one-line fix instead of a mystery. `build` needs no change; it
regenerates either way.

Cost: small. Highest value per line of code in this document.

---

## Plan D — Starter pack upgrades

**Problem:** the hardest one. A user edits `.wondev/skills/debugging/SKILL.md`. Version 0.4
ships a better version of that skill. How is it offered without destroying their edit?

Record provenance at `init` time:

```json
// .wondev/.templates.json
{
  "version": "0.1.0",
  "files": {
    "skills/debugging/SKILL.md": { "hash": "sha256:...", "from": "0.1.0" }
  }
}
```

`wondev upgrade` then classifies every starter file:

| State | Action |
| ----- | ------ |
| untouched (hash matches) | update in place, silently |
| edited by the user | **do not touch**; write `SKILL.md.new` alongside and report it |
| deleted by the user | leave deleted — that was a decision |
| new upstream template | offer to add; `--no-new` skips |

Flags: `--dry-run`, `--only <path>`, `--restore` for deliberately re-adding deleted files.

### Why not a three-way merge

A real 3-way merge is the obvious alternative and is wrong here. Merging prose produces
plausible-looking corruption: two reasonable sentences interleaved into one that instructs
an agent to do something neither author intended. A `.new` file next to the original is
unglamorous, always correct, and takes the user thirty seconds. Conflict markers inside a
file an AI agent reads as instructions are actively harmful.

Cost: the largest item here. Highest user-visible value.

## Plan E — Registry evolution and deprecation

Agents move their config paths. Windsurf's documentation already shows `.devin/` taking
precedence over `.windsurf/`, so this is not hypothetical.

Give registry entries an optional deprecation record:

```ts
deprecated?: { since: string; replacedBy?: string; note?: string }
```

- `build` warns once per run when a deprecated target is enabled.
- `wondev migrate` rewrites `targets:` from the old name to the replacement.
- The old generated file is removed automatically — stale manifest entries are already
  cleaned up on build, so this works today with no new code.
- `wondev targets --new` lists targets added since the `wondevVersion` in `wondev.yaml`:
  *"3 agents supported since you initialised."* Discovery is otherwise invisible.

---

## Plan F — Update notification

Deliberately minimal. Most usage is `npx wondev`, which already fetches the latest.

For globally installed users, add the check to a `wondev doctor` command that only runs when
invoked. **No background version ping.** A silent network call on every build would
contradict the zero-dependency, no-telemetry, fast-cold-start design, and would be the only
part of wondev that phones home.

---

## Plan G — Compatibility testing

Mechanisms that are not tested against real old projects do not work.

- `test/fixtures/schema-1/` — a project frozen at each historical schema, never edited again.
  Migrations run against these.
- Golden output files committed to the repo. A diff there is a deliberate decision to bump
  MINOR, not an accident to be rubber-stamped.
- A CI job that proves the upgrade path end to end: install the **previously published**
  version, `init` a project, install the new build, then `migrate && build && check`.
  Nothing else catches an upgrade that silently corrupts an existing project.

---

## Recommended order

| Order | Plan | Why now |
| ----- | ---- | ------- |
| 1 | **C** output-version awareness | Prevents a confusing mass CI failure the first time a renderer changes. Small. |
| 2 | **A** release contract | Cheap, and defines what every later change is allowed to do. |
| 3 | **B** version stamps | **Impossible to retrofit.** Stamp now; write migrations when needed. |
| 4 | **G** compatibility tests | Makes 1–3 real rather than aspirational. |
| 5 | **D** `wondev upgrade` | Biggest build, biggest payoff. Needs B's provenance data first. |
| 6 | **E** deprecation | Wait for the first agent to actually move a path. |
| 7 | **F** doctor | Optional. |

Items 1–3 are roughly a day and should land **before the first publish**, because all three
are about being able to identify a project after the fact. Everything from 4 down can ship
in later releases without stranding anyone.
