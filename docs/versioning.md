# Versioning contract

wondev writes files into other people's repositories. Those files get committed, reviewed,
and checked in CI. That makes the version contract unusually strict: a change that looks
cosmetic here becomes a diff in someone else's pull request.

## Three version numbers, on purpose

| Number | Where | Changes when |
| ------ | ----- | ------------ |
| package version | `package.json` | every release |
| `SOURCE_SCHEMA_VERSION` | `src/core/schema.ts` | `.wondev/` layout or frontmatter changes |
| `MANIFEST_SCHEMA_VERSION` | `src/core/schema.ts` | `.wondev/.manifest.json` shape changes |

The two schema numbers move far more slowly than the package version, and only they drive
migrations. Collapsing them into the package version would mean every patch release looked
like a format change.

## SemVer rules

**MAJOR** — a project that worked before now needs manual intervention.

- The source format changes in a way `wondev migrate` cannot handle automatically.
- A target's output path moves, so the old file must be deleted by hand.
- A CLI flag or command is removed.

**MINOR** — safe to take, but the working tree will change.

- A new target, a new starter skill, a new command or flag.
- **Any change to generated bytes**, however small.
- A source schema bump that `wondev migrate` handles.

**PATCH** — output is byte-identical before and after.

- Bug fixes in validation, error messages, or CLI output.
- Documentation, tests, internal refactoring.

## The rule that matters

> **A change to generated output is never a patch.**

Renderers are pure functions, so any edit to one changes the bytes in every project that
upgrades. Those projects run `wondev check` in CI, and `check` compares against the
manifest. A "harmless" wording tweak shipped as a patch turns every downstream pipeline red
simultaneously, on a version bump nobody read the notes for.

If you are unsure whether a change affects output, the golden tests will tell you: a diff in
`test/render.test.ts` expectations or in a fixture is the signal to bump MINOR.

## What softens the blow

The manifest records which wondev version produced each file. When the running version
differs from the recorded one, `check` says so explicitly:

```
3 generated file(s) were produced by wondev 0.1.0, but you are running 0.2.0.
Run `wondev build` to regenerate them with this version, and commit the result.
```

rather than the generic drift message. The failure still happens — it must, or the committed
files would be stale — but it reads as an upgrade step instead of a mystery.

## Deprecation

Nothing is removed without one MINOR release of warning.

1. Mark it deprecated. `build` warns once per run and names the replacement.
2. Ship at least one MINOR with the warning in place.
3. Remove it in the next MAJOR.

Target renames are gentler: add an alias from the old name to the new one and keep it
indefinitely. Aliases cost one line in the registry, and breaking someone's `wondev.yaml` to
save that line is a bad trade.
